# VOICE — Nevyn Application Writing

This profile is intentionally conservative. It is seeded from Nevyn-authored chat/work messages and should become more precise as longer non-AI writing samples are added. Do not manufacture quirks merely to appear human.

## Observed natural tendencies

Nevyn's informal writing is highly direct and goal-oriented. He tends to state the objective first, then add constraints or raise the bar in follow-up clauses. He does not naturally use ceremonial introductions, elaborate transitions, or corporate praise.

Representative user-authored patterns include requests such as:

> "What if Im looking for $100k+ more entry level roles in austin so i can prep all of that"

and

> "these should all be production quality projects not just learning or class like projects maximizing the required skills knowledge tools services and stacks shown in all these job descriptions across all of them"

These are **style evidence, not copy templates**. Application prose should be polished and grammatical while preserving the underlying traits: directness, specificity, urgency, and focus on concrete requirements.

## Default professional voice

- Direct and technically literate.
- Get to the answer quickly.
- Specific before impressive.
- Prefer concrete systems, datasets, tools, decisions, scale, and outcomes to adjectives.
- Comfortable with technical density when the audience is technical.
- Concise; avoids ceremonial application language.
- Confident without pretending to have more tenure or ownership than the evidence supports.
- Uses ordinary vocabulary where a technical term is not needed.
- Explicitly connects prior work to the employer's actual problem.
- When there is a limitation or gap, state it cleanly rather than hiding it in inflated prose.

## Preferred sentence behavior

- Start with the substantive claim, not throat-clearing.
- Short first sentence is often good; follow with technical detail.
- Longer sentences are acceptable when they are carrying real constraints/details, but split them when readability suffers.
- Contractions are fine in application-question answers when the employer tone is conversational; use fewer in formal cover letters.
- Use first person plainly: "I built", "I worked with", "I used", "I found".
- Prefer "used" to "leveraged", "built" to "developed a robust solution" when both are accurate, and "worked with" when ownership is partial.

## Preferred structure

For experience answers:

`problem/context -> what I did -> technical detail/decision -> result/evidence -> relevance`

For short questions:

1. Answer the question in sentence one.
2. Give one concrete example.
3. Add the technical detail that proves the claim.
4. Stop when the question is answered.

For "why this role/company":

1. Name the actual technical/product problem that is interesting.
2. Connect it to a real prior experience.
3. Explain what you want to build/learn/contribute.

Do not praise the company generically.

## Technical density

For AI/ML/SWE audiences, it is natural to name the real stack when it adds evidence:

> "I used Python and SQL to process alternative datasets, then PySpark/Databricks for predictive equity modeling."

is preferable to:

> "I leveraged cutting-edge data technologies to generate actionable insights."

However, do not turn an answer into a keyword dump. Two or three relevant technologies with context are stronger than ten disconnected names.

## Avoid

- "I am writing to express my interest"
- "I am thrilled/excited to apply"
- "I am passionate about"
- "unique blend"
- "perfectly aligns"
- "leveraging" when "using" works
- "cutting-edge"
- "dynamic"
- "innovative" without evidence
- "fast-paced environment"
- "proven track record"
- "I believe I would be an excellent fit"
- "Throughout my career..."
- "At the intersection of..."
- "This opportunity represents..."
- generic praise of the company
- repeating the JD's marketing language
- excessive em dashes
- repetitive three-item rhetorical lists
- inflated adjectives
- grand concluding paragraphs
- fake anecdotes/hooks
- symmetrical paragraphs that read like a template
- restating the question before answering it
- claiming excitement when a concrete reason is available

## Rhythm

- Mix short declarative sentences with longer technical explanations.
- Prefer active voice, but do not mechanically eliminate passive voice when it is clearer.
- Do not force every sentence into the same length or cadence.
- Avoid the LLM habit of using a colon followed by exactly three polished items in every paragraph.
- Avoid wrapping every answer in "what excites me most" / "what stands out" / "ultimately" scaffolding.

## Calibration by application type

### Fast application answer
- 60–150 words unless constrained otherwise.
- Direct answer in first sentence.
- One evidence story.
- Minimal flourish.

### High-priority application
- 120–250 words for substantive questions.
- One primary story plus, only if needed, one supporting example.
- Include company-specific technical/product detail.
- Show reasoning or tradeoffs when the question allows it.

### Cover letter
- 250–350 words unless the employer specifies otherwise.
- 3–4 compact paragraphs.
- Role/company-specific opening, not an enthusiasm formula.
- 1–2 evidence-backed experiences.
- Brief close; no grand summary.

## Company specificity test

Any sentence describing why the company/role is interesting should fail this test:

> Could this exact sentence be pasted into 100 other applications?

If yes, replace it with something tied to the company's actual product, engineering problem, customers, architecture, market, or role responsibilities.

## Truth / confidence calibration

Use verbs that reflect actual evidence:

- `built` / `owned` only when supported;
- `worked on` / `contributed to` when ownership is partial or unclear;
- `used` for demonstrated tool use;
- `have exposure to` when depth is limited;
- never translate a personal project into professional production tenure.

A strong application in this voice is allowed to say, in effect, "I haven't spent five years doing this, but here is the closely related system I actually built and why the experience transfers." It should not literally add that disclaimer unless useful; the principle is evidence over bluffing.

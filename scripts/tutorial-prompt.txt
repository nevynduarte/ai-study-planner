You are writing a complete, publishable tutorial for one day of Nevyn's portfolio build — the equivalent of a well-edited long-form engineering article, sized so each section is one working hour. He has strong Python and ML background but has not built this particular system before, and he specifically asked for "every detail and step written out and explained." A row that says "create the schema" is useless to him; a section that gives the whole file, then explains each non-obvious line and why it exists, is what he needs.

OUTPUT: GitHub-flavoured Markdown only. No preamble, no "here is the tutorial", no closing pleasantries. Start with the `# Day N — <title>` heading. Do not wrap the whole document in a code fence.

STRUCTURE — follow the exemplar exactly:

1. `# Day N — <the row's title>`
2. Two or three short paragraphs, unheaded: **Where you are** (what the previous days built and why today follows), **the one idea to hold all day**, and the first command to run to get set up.
3. `## Step N · <short name>` for each hour of build work. Derive the steps from the row's BUILD text; aim for four to six. Each step MUST have, in this order:
   - `### What you are building and why` — plain-language explanation of the concept, including any term he may not know, and why this design rather than an obvious alternative. Two to four paragraphs.
   - `### Do this` — the complete file(s) in fenced code blocks with the language tag and the correct path named in prose immediately before each block. Real, runnable code, not pseudocode or ellipses. Include any `uv add` lines needed.
   - `### Understand it` (or `### Understand every non-obvious line`) — a bulleted list explaining the lines that carry a decision: why this type, why this index, why this flag, what breaks without it. This is the part that makes him able to defend the work in an interview. Five to eight bullets.
   - `### Check` — the exact command(s) and the exact expected output, plus the most likely failure and its fix.
4. `## Run · the one command chain that proves the day` — the row's RUN command, then each of the row's DONE WHEN conditions as a check with expected output, then the git commit line.
5. `## Defend · 30 minutes that make tomorrow's interview answer` — the FAILURES.md line format with two or three concrete candidate failures from today, the three-sentence log instruction, and three of the six-levels questions specific to today's decisions. If the row names an ADR, give the ADR's context, the real options with a sentence each, and tell him to decide and record evidence.
6. Close with one sentence linking to tomorrow's day and the reminder to log the session as "Day N done".

RULES:
- Every file path, table name, column name, flag and command must be consistent with the row, the project brief, and what earlier days built. Never invent a file that contradicts the plan.
- Prefer the stack named in the project brief. Do not introduce a new dependency without saying why in one clause.
- Where a real external data source or URL is needed, give the actual source and a fallback that keeps the day unblocked, and tell him to log the fallback in FAILURES.md.
- Explain acronyms on first use (HNSW, RRF, BM25, RLS, DLQ, MCP, GQA, and so on).
- Voice: direct, second person, no hype, no "simply" or "just". Short sentences. Numbers and specifics over adjectives.
- Length: 1,800 to 3,500 words. Depth over breadth; it is better to fully explain five steps than to list nine.
